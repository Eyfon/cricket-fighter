# 蛐蛐格斗设计总规范

版本：`1.0`  
适用范围：游戏玩法、战斗系统、角色设计、地图设计、招式数值、AI、动画贴图、音效和验收流程。  
实现参考：`js/combat.js`、`js/combat-world.js`、`js/roster.js`、`js/maps.js`、`js/animation-data.js`。

这份文档是新增内容的总入口。具体数值以代码和自动校验为准；文档、角色配置和运行行为发生冲突时，必须修复冲突，不能只修改说明。

## 1. 设计目标

游戏是一个打开网页即可游玩的本地 1 对 1 街机格斗游戏。核心体验是：

1. 六个功能键即可完成移动、拳脚、闪避、技能和大招。
2. 普通拳脚简单易懂，角色差异集中在技能、距离、节奏和风险。
3. 每次命中都能读懂来源、受击方向和下一步反制方式。
4. 角色动作连续，脚底基准稳定，画面不使用拖影和交叉淡化。
5. AI 对战可以产生观赏性，但玩家操作仍然遵循同一套战斗规则。
6. 所有机制适合静态网页部署，不依赖服务器、账号或网络连接。

设计中禁止加入会破坏上述目标的内容：隐藏的全局伤害倍率、未说明的无敌、无法反制的无限连、只在 AI 中存在的特殊规则、自动连发、没有实际动作反馈的技能。

## 2. 术语和规范级别

文档中的词语含义：

- **必须**：代码、配置和验收都必须满足。
- **应当**：默认要求；若要偏离，必须在角色设计稿中说明原因。
- **可以**：可选实现，不代表引擎已经支持。
- **帧**：固定 60Hz 模拟中的一个更新单位，约 16.7ms。
- **动作槽位**：角色可以使用的输入位置，如 `punch`、`skill2`、`super`。
- **攻击**：有前摇、有效阶段和后摇的动作。
- **控制**：硬直、击退、击飞、倒地、抓取等限制行动的效果。
- **抗打断**：抵抗控制的条件，不等于免伤或无敌。

新增机制必须同时更新：

1. 角色数据和 schema 校验。
2. 战斗引擎和渲染表现。
3. 角色设计稿或战斗规则文档。
4. 自动化测试和至少一个浏览器验收场景。

新增地图还必须遵守 [地图设计与接入规范](./MAP-SPEC.md)，新增角色还必须遵守 [角色接入规范](./CHARACTER-SPEC.md)。

## 3. 游戏流程和模式

### 3.1 流程

```text
主界面 → 模式选择 → 角色选择 → 地图与规则 → VS/战斗 → KO演出 → 结算
```

结算阶段只能提供“返回”和“重新开战”。重新开战沿用本场角色、地图和规则；返回回到选人或模式流程。

### 3.2 模式

| 模式 | 玩家控制 | 对手 | 规则 |
| --- | --- | --- | --- |
| 电子斗蛐蛐 | 无 | 本地 AI | 双方使用同一战斗引擎和输入结构 |
| 人机 | P1 | P2 AI | AI 不获得额外伤害或无敌 |
| 本地双人 | P1、P2 | 另一名玩家 | 两组键位同时有效 |
| 练习 | P1 | 待机、站防或蹲防木桩 | 可开启无限能量，不计胜场 |

### 3.3 回合规则

- 默认时间：60 秒；可选 30、60、90 秒或无限。
- 默认胜局：2 局；可选 1、2、3 局。
- 默认生命：100；双方共用 1、2、3、5 倍生命倍率。
- 生命倍率只改变 `maxHp`，不改变任何招式伤害、硬直或击退。
- 时间结束比较剩余生命；相同则为平局，不增加胜场。
- 生命归零后冻结正常战斗，播放最终一击、倒地、KO、胜利语音和结算演出。
- 新回合重置 HP、能量、动作、硬直、倒地和扫腿保护，保留胜场。

## 4. 输入标准

| 功能 | P1 | P2 |
| --- | --- | --- |
| 左右移动 | A / D | ← / → |
| 跳跃 | W | ↑ |
| 防御 | S | ↓ |
| 拳 | J | 小键盘 1 |
| 脚 | K | 小键盘 2 |
| 闪避 | L | 小键盘 3 |
| 技能一 | U | 小键盘 4 |
| 技能二 | I | 小键盘 5 |
| 大招 | O | 小键盘 6 |
| 暂停 | Esc | Esc |

方向以角色面朝方向为准：

- 单按后方向：后退。
- 下方向：站立防御。
- 下＋后：蹲防，降低受击框并可挡扫腿。
- 前＋拳/脚：地面方向攻击；空中按前与拳脚仍按空中普通攻击处理。
- 下＋拳：上勾拳。
- 下＋脚：扫腿。
- 上方向只负责跳跃，不能触发技能。

攻击键按下沿触发，长按不得自动重复。方向组合优先级为：下＋攻击高于前＋攻击；方向防御不能覆盖下＋攻击。

## 5. 角色设计标准

### 5.1 角色必须填写的资料

每个角色必须有：

- 唯一 `id`、中文名、短定位、完整介绍。
- 主色 `color`、辅助色 `accent`。
- 移动速度 `speed`、起跳速度 `jump`。
- 受击框 `width`、`height`。
- AI 偏好距离、退避距离和招式权重。
- 九个动作槽位：拳、脚、前拳、前脚、下拳、下脚、技能一、技能二、大招。
- 所有动作状态素材：待机、行走、跳跃、站防、蹲防、受击、倒地、KO、闪避及九个攻击状态。
- 每个技能的用途、优势、弱点、反制方式和画面表现。
- 素材来源、生成提示词、裁切方式和授权记录。

### 5.2 角色定位

新角色必须选择一个主定位和一个副定位：

| 定位 | 主要优势 | 必须存在的弱点 |
| --- | --- | --- |
| 远程牵制 | 投射物、距离控制 | 被近身后风险高，技能有前摇 |
| 近身压制 | 短距离连段、硬直 | 手短或怕跳跃/闪避 |
| 抓取 | 抓取、位置控制 | 抓空后摇，不能抓空中目标 |
| 对空 | 上勾、升空、截击 | 地面横向压制较弱 |
| 突进 | 快速接近、抢回合 | 打空后摇明显 |
| 范围控制 | 身边爆发、落点攻击 | 需要正确站位或能量 |

角色不得同时拥有所有定位的最佳能力。每个角色至少要有一个明确的可反制点。

### 5.3 基础攻击

六种基础攻击由 `commonMoves` 统一提供，角色设计不得私自改写基础伤害、硬直、取消窗口和资源规则。角色可以通过不同动画表达重量感，但判定和基础节奏保持一致。

| 动作 | 伤害 | 前摇/有效/后摇 | 设计用途 |
| --- | ---: | --- | --- |
| 直拳 | 4 | 6/4/5 | 快速起手、确认、取消 |
| 中踢 | 6.5 | 10/5/7 | 中距离牵制 |
| 前拳 | 8 | 11/7/8 | 接近和压位 |
| 前脚 | 8.5 | 12/8/9 | 长距离突进 |
| 上勾拳 | 7 | 9/7/8 | 对空、击飞 |
| 扫腿 | 7 | 10/6/8 | 下段、击倒 |

### 5.4 技能槽位

技能一和技能二都消耗 1 点能量，没有时间冷却。大招消耗 3 点能量，没有普通时间冷却，但受动作和资源限制。

每个技能必须明确以下内容：

- 使用距离和目标条件。
- 前摇、有效阶段、后摇。
- 伤害分段和总伤害。
- 是否投射物、范围爆发、突进、上升或抓取。
- 是否击飞、倒地、破防或抓取。
- 能被哪些攻击打断，能打断哪些动作。
- 对手可以怎样防御、跳跃、闪避或反击。
- AI 在什么距离和情境下选择它。

## 6. 战斗数值标准

### 6.1 伤害和能量

- 伤害直接写入招式配置，不允许全局乘数。
- 普通拳脚伤害应保持低，避免一套普通攻击直接结束回合。
- 防御默认承受 25% 芯片伤害，芯片可以造成 KO。
- 每 100 蓄能获得 1 点，最多 3 点。
- 技能一、技能二 `cost = 1`；大招 `cost = 3`；基础攻击 `cost = 0`。
- 新技能默认 `cooldown = 0`，不设计普通技能冷却。
- 多段、投射物、抓取伤害之和必须等于配置的 `damage`。

### 6.2 帧数和硬直上限

- 普通拳硬直不超过 12 帧。
- 普通脚硬直不超过 16 帧。
- 方向攻击、技能和特殊动作硬直不超过 24 帧。
- 大招硬直不超过 30 帧。
- 角色攻击必须留下可行动窗口，不能靠重复硬直实现无限压制。
- 连续受击会逐步降低硬直，达到压力阈值后触发脱身窗口。

### 6.3 击飞、倒地和扫腿保护

- `launch > 0` 表示击飞初速度；击飞不自动等于倒地。
- `knockdown: true` 表示命中后进入倒地流程。
- 倒地基础时长为 0.72 秒，必须播放失衡、下坠、落地、躺倒和起身过渡。
- 扫腿成功后 5 秒内不能再次被扫腿击倒。
- 扫腿保护不提供免伤、免硬直或免抓取。
- 被保护抵消的扫腿不算有效倒地，不能用于打断技能。

## 7. 防御、打断和反制

### 7.1 防御

- 站防由下方向触发。
- 蹲防由下＋后触发，受击框高度为站立高度的 80%。
- 蹲防可以挡扫腿；站防不能挡低段扫腿。
- 蹲防必须有独立两帧以上素材：蹲姿防守和格挡受力。
- 防御期间不能移动或开始攻击。

### 7.2 打断矩阵

| 正在释放 | 普通拳脚 | 击飞攻击 | 倒地攻击 | 技能一/二 | 大招 |
| --- | --- | --- | --- | --- | --- |
| 普通攻击 | 可打断 | 可打断 | 可打断 | 可打断 | 技能规则决定 |
| 技能一/二 | 不打断 | 可打断 | 可打断 | 可打断 | 可打断 |
| 大招 | 不打断 | 不打断 | 不打断 | 可打断 | 可打断 |

抗打断只抵抗控制，仍然承受伤害；生命归零始终正常 KO。抓取也按是否附带击飞或倒地判断能否打断技能。

### 7.3 同帧命中和墙角

- 双方同帧近战接触时，进入有效阶段更早的一方优先命中。
- 完全同帧使用固定玩家顺序，不能互相同时打出硬直。
- 墙角反推只适用于贴身近战：水平距离不超过 140、垂直距离不超过 100。
- 投射物、范围爆发、落地砸击和抓取不会反推施放者。

## 8. 状态词典

| 状态 | 行为限制和表现 |
| --- | --- |
| `idle` | 待机，可移动和出招 |
| `walk` | 移动，必须有交替迈步帧 |
| `jump` | 空中，受重力影响，可使用普通拳脚 |
| `guard` | 站防，降低可防御攻击伤害 |
| `crouchGuard` | 蹲防，降低受击框，可挡扫腿 |
| `hurt` | 受击硬直，不能出招 |
| `knockdown` | 倒地流程，不能出招 |
| `dodge` | 闪避无敌前段，不能攻击 |
| 攻击槽位状态 | 执行该动作的前摇、有效、后摇 |
| `ko` | 生命归零，进入回合结束流程 |

技能状态还可能有 `capturedBy`、`grabbing`、`burstVisual`、`sweepImmunity` 等运行标记。运行标记不能直接作为玩家新技能配置字段，必须先扩展 schema 和测试。

## 9. AI 设计标准

AI 只使用公开的输入接口，不调用特殊作弊 API。每个招式填写：

- `ai.role`：`poke`、`antiAir`、`approach`、`finisher`、`ranged`、`grapple`。
- `ai.weight`：同一情境下的选择权重。
- `range`：AI 选择该招式的参考距离。
- `minRange`：太近时不选择远程招式。

AI 必须遵守地面限定、能量点、硬直、闪避冷却和抓取目标条件。AI 不得拥有玩家没有的伤害倍率、额外能量或隐形无敌。

### 9.1 角色 AI 风格

- 苍岚：优先中远距离，使用直线气功球；距离过近时后退或使用范围爆气。
- 赤锋：优先接近，近距离选择抓取、爪击和跳锤；远距离应尝试接近而不是连续空放抓取。

## 10. 动画和贴图标准

### 10.1 目录

资源按人物分类：

```text
assets/characters/<character>/
├── common/
├── skill1/
├── skill2/
├── super/
└── manifest.json
```

完整目录见 `docs/SPRITE-DIRECTORY.md`。每个动作可以是一张独立多帧 PNG；禁止新增一个包含无关角色和无关动作的巨大总图。

### 10.2 动作帧

每个攻击至少提供：

- 蓄势或前摇。
- 出手或有效帧。
- 命中保持帧。
- 收招或恢复帧。

行走至少四帧，左右脚必须交替。蹲防至少两帧。倒地至少包含失衡、倒下、躺倒和起身过渡。

### 10.3 贴图硬性要求

- 透明背景，人物或特效不能跨帧边界。
- 每个角色保持统一头身比例、脚底基准和显示比例。
- `originY` 用于修正脚底，不允许按每帧外接框重新缩放人物。
- 人物和投射物、气焰、命中火花分层绘制。
- 禁止拖影、残影、交叉淡化和同一帧重复绘制两个角色。
- 裁切后必须检查边缘是否串入邻帧颜色或特效。
- `manifest.json` 必须记录来源、帧矩形、比例、锚点和阶段映射。

## 11. 音效和演出标准

- 大厅、选人、战斗、结算始终有 BGM；地图有独立战斗音乐。
- 普攻、脚击、命中、防御、闪避、投射物、范围爆发、抓取和大招有可区分音色。
- 大招启动需要短暂时停、镜头收缩和强烈音效；不添加额外语音喊招。
- KO 播报必须在倒地演出后出现，胜负语音必须和实际胜者一致。
- 音频默认开启，用户可以静音或调节音量。
- 音效不能决定战斗结果；声音失败时战斗仍可运行。

## 12. 新角色制作流程

### 阶段 A：设计

1. 填写 `docs/templates/CHARACTER-BRIEF.md`。
2. 选择主定位、副定位和明确弱点。
3. 为技能一、技能二、大招写出用途、距离、反制和动作描述。
4. 检查是否复用了已有机制；新机制单独记录。

### 阶段 B：数值

1. 先配置伤害、前摇、有效、后摇、硬直、击退和能量消耗。
2. 检查 stun、cost、cooldown、伤害分段和 schema 限制。
3. 用近战、远程、跳跃、防御、闪避、墙角六种情境做纸面测试。

### 阶段 C：素材

1. 按角色目录生成 common、skill1、skill2、super 资源。
2. 检查透明边缘、脚底、比例、帧间距和特效分层。
3. 更新 `manifest.json` 和 `animation-data.js`。

### 阶段 D：接入

1. 编辑 `js/roster.js`，复制角色并使用唯一 id。
2. 运行 `assertRoster`，修复所有 schema 错误。
3. 添加动作、判定、资源、AI 和保护机制测试。
4. 更新角色说明、技能图鉴和目录说明。

### 阶段 E：验收

必须验证：

- P1、P2 键位和左右朝向。
- 地面、空中、墙角、双方同时攻击。
- 站防、蹲防、扫腿、防御芯片。
- 技能能量扣除、无冷却、打断和结束。
- 击飞、倒地、抓取、脱身保护。
- AI 的距离选择、能量判断和反制。
- 所有动作是否有前后过渡、是否串边、是否变大。
- 移动端触控和窗口失焦暂停。
- `npm test`、`npm run build` 和浏览器 smoke。

## 13. 验收清单

新角色合入前，以下项目必须全部通过：

- [ ] 唯一 id、定位、弱点、素材来源完整。
- [ ] 九个动作槽位全部存在且 cost 正确。
- [ ] 所有动作状态素材存在并通过 schema。
- [ ] 基础攻击未私自改数值。
- [ ] 技能一和技能二各消耗 1 点，无普通冷却。
- [ ] 大招消耗 3 点，打断规则明确。
- [ ] 总伤害和分段伤害相等。
- [ ] 所有击飞、倒地、抓取、投射物条件可反制。
- [ ] 走路、蹲防、攻击、倒地动作连贯。
- [ ] 没有串边、拖影、人物缩放跳变。
- [ ] AI、P1、P2 都能使用该角色。
- [ ] 测试、构建、浏览器检查通过。

## 14. 设计变更记录

任何改变全局规则的修改都要记录：

```text
日期：YYYY-MM-DD
变更：
影响：
涉及代码：
新增/修改测试：
是否影响已有角色：
```

这样可以避免角色文档、实际代码和图鉴描述逐渐分叉。
